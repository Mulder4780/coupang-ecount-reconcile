# 유사 앱 전수조사와 반영 — 2026-07-31

사용자 지시: "이 앱과 비슷한 다른 앱들 전수조사해서 좋은 점 있으면 가져와서 반영하고
UI/UX도 반영해."

## 0. 조사보다 **우리 기록**이 먼저다

CLAUDE.md 규칙대로 `ledger_db.ux_summary()`(최근 7일, 962건)를 먼저 읽었다.
남의 앱에서 좋아 보이는 것을 가져오기 전에, **우리 사용자가 실제로 어디서 막히는지**가
먼저다. 기록이 가리킨 것은 하나였다 — **속도**.

| 주소 | 최악 1회 | 느린 호출 수 |
|---|---:|---:|
| `/api/notifications` | **59.3초** | 22 |
| `/api/staff/activity` | 41.4초 | 2 |
| `/api/exec_report` | 31.0초 | 31 |
| `/api/codes` | 17.3초 | 17 |
| `/api/tasklog` | 15.2초 | 19 |
| `/api/calendar` | 15.1초 | 1 |
| `/api/brand` | 11.4초 | 2 |

- 화면별 방문: dash 52 · ryu 44 · settle 28 · check 27 · daily 16 · worklog 7
- 오류: `/api/status` 2 · `/api/notifications` 1 · **빈손검색 0건**(검색은 잘 맞고 있다)

`/api/notifications` 는 로컬 파일 두 개만 읽는 **가벼운** 호출인데 59초가 나왔다.
서버는 이미 `ThreadingHTTPServer` 라 구조 문제가 아니고, Z: 네트워크 드라이브 지연과
엑셀 파싱(GIL을 오래 쥔다)에 **가벼운 호출이 밀린 것**이다. 화면 쪽에서 이 지연을
없앨 수는 없다 — 그래서 **기다리지 않게** 만드는 쪽으로 갔다.

## 1. 조사한 앱과 그 앱들이 잘하는 것

현장서비스(FSM)·설비보전(CMMS) 계열에서 모바일 평가가 높은 것들을 봤다.

| 앱 | 배울 점 | 우리에게 |
|---|---|---|
| **UpKeep** | 모바일 우선 구조로 1위 평가 | 이미 모바일 우선(PWA) — 유지 |
| **Limble** | 카드형(칸반) 목록, 클릭 수 줄이기 | 부분 채택(스켈레톤·목록은 이미 카드형) |
| **MaintainX** | 작업지시를 **대화 스레드**처럼 | 보류 — 아래 3항 |
| **Jobber / Housecall Pro / ServiceTitan** | 기사용 앱은 소비자 앱처럼 익숙하게 | 유지 |
| 공통 권고 | 오프라인 우선 · 한 손 조작 · 2분 안에 끝나는 작업 · 사진 첨부 | **오프라인 우선은 오늘 콜드스타트까지 완성** |

체감 성능 쪽 공통 권고는 세 가지로 모인다: **스켈레톤 화면**, **낙관적 UI**,
**stale-while-revalidate**(옛 값 먼저·조용히 갱신).

## 2. 반영한 것

### (1) stale-while-revalidate — 옛 값을 먼저 그린다
`api()` 한 곳에만 넣었다. 호출부가 화면 곳곳에 흩어져 있어 하나씩 고치면 새 화면에서
또 빠뜨린다(오프라인 큐를 `window.fetch` 한 곳에 넣은 것과 같은 이유).

- 읽기 12개 주소만 대상. **쓰기(POST)는 캐시하지 않는다.** 목록에 없으면 예전 그대로.
- 15초 안에 받은 값이면 다시 부르지 않는다 → 재렌더 되돌이 차단.
- 값이 오래됐으면 **즉시 옛 값을 돌려주고** 뒤에서 새로 받아 화면을 다시 그린다.
- ★ **"몇 분 전 자료 · 갱신 중" 칩을 반드시 같이 띄운다.** 그동안 `/api/` 를 일부러
  캐시하지 않은 이유가 "옛 숫자가 최신인 척 남는다" 였다. 숨기지 않고 **표시로** 푼다.

실측(로직 격리 검증):

| 상황 | 응답 | 네트워크 |
|---|---:|---:|
| 캐시 없음 | 304ms | 1회 |
| 방금 받은 값 | **0ms** | 0회 |
| 10분 된 값 | **0ms**(칩: "10분 전 자료 · 갱신 중") | 뒤에서 1회 |
| 갱신 직후 재호출 | 0ms | **0회**(되돌이 없음) |

### (2) 정산 화면: 직렬 8개 → 병렬
`loadSettle()` 이 서로 아무 관계 없는 API **8개를 한 줄로 세워** 부르고 있었다.
각 1~3초면 화면이 10초를 넘긴다. `Promise.all` 로 바꿔 **가장 느린 하나**만 기다린다.
실패는 각자 삼키던 방식 그대로 유지했다(한 곳이 죽어도 화면은 뜬다).

### (3) 스켈레톤 화면
`로딩...` 글자 4곳을 들어올 모양대로 바꿨다. 기다리는 시간이 같아도 짧게 느껴진다.
`prefers-reduced-motion` 을 존중해 애니메이션을 끈다.

## 3. 일부러 **반영하지 않은** 것

- **MaintainX식 대화 스레드 작업지시** — 우리 작업 원문은 이미 밴드·카톡에 있고,
  앱은 그것을 **원장과 대조**하는 자리다. 스레드를 또 만들면 원문이 두 곳이 된다.
- **GPS·기사 위치 추적** — 조사한 앱 다수가 밀지만, 요구된 적이 없고 근로감시 소지가 있다.
  필요해지면 그때 사용자 판단으로 넣는다.
- **결제·견적 발행** — 이 업무는 ERP(이카운트)가 정본이다. 앱이 끼면 원본이 둘이 된다.
- **칸반 보드** — 기존 목록이 이미 카드형이고, 상태 이동은 원장 규칙(증빙 필요)에
  묶여 있어 드래그로 옮기면 안 된다.
